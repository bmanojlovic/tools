# OBS Go Vendored Dependency CVE Fix

## Purpose
Handle SUSE Bugzilla security tickets where a package embeds a vulnerable Go dependency
(typically `golang.org/x/net`, `golang.org/x/crypto`, etc.) and needs updating.

## When to Use
- Bug title contains "VUL-0" or "VUL-1" with CVE numbers
- Description mentions "embedded package" / "vendored dependency"
- Package has a Go agent component (like zabbix-agent2)

## Workflow

### Step 1: Understand the Ticket

From the bugzilla ticket extract:
- **CVE IDs** (e.g., CVE-2026-25680)
- **Affected Go module** (e.g., `golang.org/x/net/html`)
- **Current vendored version** (e.g., 0.17.0)
- **Affected codestreams** (e.g., openSUSE:Factory, Backports:SLE-15-SP7)
- **bsc# number** (the bug ID itself, e.g., bsc#1267045)

### Step 2: Check if Version Upgrade Fixes It

The most common fix is a version bump — upstream usually updates vendored deps in releases
that come after CVE publication dates.

Check:
1. CVE publication date vs latest upstream release date
2. If upstream released AFTER the CVE → likely fixed
3. Verify by checking `go.mod` in the new version's source:

```bash
# After quilt setup / tarball extraction:
grep "golang.org/x/net" <source>/src/go/go.mod
```

Compare vendored version against the fix version listed in the Go vulnerability database:
```
https://pkg.go.dev/vuln/GO-2026-NNNN
```

### Step 3a: Version Bump Resolves It

If the latest upstream version includes the fix (check `go.mod` via quilt setup):

1. Perform standard version upgrade (see `osc-package-upgrade` skill)
2. Add CVE/bsc# references to `.changes` entry
3. Build, commit, submit as usual

### Step 3b: Use `obs-service-go_modules` with `replace` (Preferred)

When the upstream version does NOT fix the vulnerable vendored dep, use
`obs-service-go_modules` to re-vendor with the fixed version. This is the
proper openSUSE/OBS way — no manual patching, reproducible, future-proof.

**Prerequisites**: `obs-service-go_modules` installed (`rpm -q obs-service-go_modules`)

1. Create/update `_service` file in the package directory:

```xml
<services>
  <service name="go_modules" mode="manual">
    <param name="archive">PACKAGE-VERSION.tar.gz</param>
    <param name="subdir">src/go</param>
    <param name="replace">golang.org/x/net=golang.org/x/net@v0.55.0</param>
    <param name="compression">gz</param>
  </service>
</services>
```

Key parameters:
- `archive` — the source tarball containing go.mod
- `subdir` — path within tarball to the Go module (where go.mod lives)
- `replace` — module replacement in format `old=new@version`
  (multiple `<param name="replace">` lines for multiple replacements)
- `compression` — gz/xz/zstd for the output vendor.tar.gz

2. Run the service:
```bash
osc service manualrun
```

This generates `vendor.tar.gz` with the patched dependency.

3. Add `vendor.tar.gz` as a Source in the spec:
```
# Generated by obs-service-go_modules with replace for CVE fixes (bsc#NNNNNNN)
Source17:       vendor.tar.gz
```

4. In `%prep`, overlay the vendor after patches:
```
# Overlay vendored Go dependencies with CVE-fixed versions (bsc#NNNNNNN)
%{?_with_golang:tar xzf %{SOURCE17} -C src/go/}
```

5. Register files:
```bash
osc ar
```

**Benefits**:
- No giant binary patch files
- `_service` file documents exactly what was replaced and why
- Easy to revert: remove `replace` param when upstream bumps the dep
- Future CVEs in same package: just add another `replace` line + re-run
- Reproducible on OBS build servers

### Step 3c: Manual Quilt Patch (Last Resort)

Only if `obs-service-go_modules` cannot be used (e.g., unusual project layout):

1. Use quilt to create patch, `go get` + `go mod vendor` inside source tree
2. `quilt refresh` to capture changes
3. Add patch to spec

This produces large patches and is harder to maintain — avoid if possible.

### Step 4: .changes Entry Format for Security Fixes

Always include both `bsc#` and CVE references:

```
- Fix <module> vendored dependency vulnerabilities
  (bsc#NNNNNNN, CVE-YYYY-AAAAA, CVE-YYYY-BBBBB, CVE-YYYY-CCCCC)
```

If combined with a version upgrade, put the security line right after the version header:

```
- Update to version X.Y.Z LTS
- Fix golang.org/x/net/html vendored dependency vulnerabilities
  (bsc#1267045, CVE-2026-25680, CVE-2026-25681, CVE-2026-27136,
   CVE-2026-42502, CVE-2026-42506)
```

### Step 5: Submit

For security fixes, submit as usual via `osc sr`. The bsc# reference in .changes
links the fix to the security tracker automatically.

## Notes

- Most Go vendored CVE tickets are resolved by a simple version bump
- The Go vulnerability database at `https://pkg.go.dev/vuln/` lists fixed versions
- Zabbix agent2 is the Go component; the C-based server/proxy/agent are not affected by Go CVEs
- CVSS score from the whiteboard field indicates severity/priority
- Always verify the fix by checking `go.mod` in the new tarball after extraction
